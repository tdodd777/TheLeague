# Contributing

Thanks for looking at this. A few things to know before you open a PR.

## What this project is

A template. Point it at one Sleeper league ID and it builds a static site for that league: standings, matchups, head-to-head, records, season history, drafts, transactions, trades, manager profiles, awards, a constitution page, and FantasyCalc-driven dynasty rankings. No database, no backend, no per-request server. Data is pulled from the public Sleeper API at build time by `npm run ingest` and written to `data/`.

## What this project is not

It is not a multi-tenant SaaS. There is no concept of multiple leagues sharing one deployment, no login system, and no admin panel. Each fork serves exactly one league, configured through env vars and the files in `src/config/`. If a change only makes sense for a site hosting many leagues at once, it does not belong here.

## In scope

- Bug fixes: something in the codebase is wrong for any valid Sleeper league, not just an edge case in one person's data.
- Additional Sleeper API coverage: league settings, scoring formats, or roster configurations the ingest pipeline does not yet handle correctly.
- New deploy targets or host documentation (Netlify, Vercel, Cloudflare Pages, etc.), as long as the app itself stays free of host-specific runtime code.
- Accessibility fixes: keyboard navigation, screen reader labeling, color contrast, focus states.
- Documentation: README, SETUP.md, ARCHITECTURE.md, or this file, when they are wrong, unclear, or out of date.
- Performance and build-time improvements that do not change behavior.

## Out of scope

- Changes that only make sense for one specific league's rules, roster count, or scoring (those belong in `src/config/`, not in application code).
- A database, a runtime API layer for data fetching, user accounts, or anything else that turns this from a static build into a hosted service. The three-lifetime model (ingest at build time, static JSON, browser-direct polling of Sleeper for live scores) is intentional. See `ARCHITECTURE.md` before proposing anything that adds a persistent backend.
- Redesigns. Open an issue to discuss a visual or UX change before sending a PR that touches the design system.

If you are not sure whether something is in scope, open an issue first and ask.

## Local setup

```bash
git clone <your fork>
cd <your fork>
npm install
echo "SLEEPER_LEAGUE_ID=your_league_id" > .env
npm run ingest
npm run dev
```

`npm run ingest` is required before `npm run dev` on a fresh checkout: `data/` starts empty, and pages that read it will throw until it has run at least once. Node 20 or later is required (see `engines` in `package.json`).

## Before opening a PR

Run all three of these and make sure they pass:

```bash
npm run typecheck
npm run lint
npm run test
```

`typecheck` runs `tsc --noEmit` under strict TypeScript. `lint` runs ESLint. `test` runs the unit test suite (`tsx --test`) covering the rankings engine and the ingest/data layer; one of those tests imports `scripts/ingest.ts`, so `SLEEPER_LEAGUE_ID` must be set in the shell (see Local setup above) or `npm run test` fails the same way `npm run ingest` does, it doesn't need to be a real league ID. If you changed anything visual, also check it at a phone-width viewport; there is no visual regression suite, so that check is manual.

## Data files

Everything under `data/league-cache/`, `data/values-snapshots/`, and `data/players.json` is gitignored. It is fork-specific, regenerated by `npm run ingest`, and should never be committed, not even in a PR that changes ingest behavior. If your change affects what gets written there, describe the effect in the PR description instead of committing the output.

## Reporting a bug

Open an issue using the bug report template under `.github/ISSUE_TEMPLATE/`. Include the route, the league phase (in-season, off-season, pre-draft), and whether `npm run ingest` completed successfully. For feature ideas, use the feature request template in the same folder, and say whether the change would help most forks or only your league (a league-specific need usually means a config option, not new code).
